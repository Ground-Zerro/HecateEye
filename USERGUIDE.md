# Око Гекаты · обфускатор — руководство пользователя

`hecate-eye` маскирует трафик L2TP так, чтобы на проводе он
выглядел обычным UDP без узнаваемой сигнатуры протокола. Сам туннель —
аутентификацию, маршрутизацию, весь PPP — по-прежнему поднимают настоящие
`pppd`/`xl2tpd`.

## Быстрый старт

Типовой случай: есть VPS с `xl2tpd` и роутер, с которого L2TP не проходит. Нужны два запуска — по одному на каждой стороне.

**На сервере** (рядом с настоящим `xl2tpd`):

```sh
./hecate-eye --mode relay --role server \
  --listen 0.0.0.0:41850 \
  --target 127.0.0.1:1701 \
  --key 'общий-секрет'
```

**На роутере** (рядом с настоящим L2TP-клиентом):

```sh
./hecate-eye --mode relay --role client \
  --local 127.0.0.1:1701 \
  --peer <ip-сервера>:41850 \
  --key 'общий-секрет' \
  --session-id office-router
```

После этого в настройках штатного L2TP-клиента роутера адрес сервера
меняется с реального на `127.0.0.1` — клиент теперь стучится в
`hecate-eye`, а тот уже идёт наружу.

Ключ должен **точно совпадать** на обеих сторонах. `--session-id` —
наоборот, у каждого клиента свой; серверу его знать заранее не нужно.

## Установка

В каталоге `bin/` лежат готовые статические бинарники без внешних
зависимостей — `x86_64`, `mips`, `mipsel`, `aarch64`. Скачайте нужный
прямо на целевую машину и сделайте исполняемым:

```sh
wget -O /opt/bin/hecate-eye \
  https://raw.githubusercontent.com/Ground-Zerro/HecateEye/main/bin/hecate-eye-mipsel
chmod +x /opt/bin/hecate-eye
```

Либо скопируйте из клона репозитория:

```sh
scp bin/hecate-eye-mipsel root@192.168.1.1:/opt/bin/hecate-eye
```

Для MIPS-роутеров важно не перепутать порядок байт: `mipsel` —
little-endian (большинство), `mips` — big-endian. Неверный вариант не
запустится, выдав невнятную ошибку оболочки вместо понятного сообщения.

Собрать из исходников:

```sh
git clone https://github.com/Ground-Zerro/HecateEye.git
cd HecateEye

make              # под текущую архитектуру
./cross-build.sh  # все четыре целевые архитектуры в bin/
```

Кросс-сборка идёт через musl, для MIPS — **soft-float** тулчейнами:
userspace роутерных прошивок собран soft-float, а часть встраиваемых ядер
не эмулирует инструкции FPU вовсе. Обычный `mipsel-linux-gnu-gcc` даёт
hard-float бинарь, который на роутере не запустится.

## Как это работает

```
настоящий клиент  →  hecate-eye          →  интернет  →  hecate-eye      →  настоящий сервер
(L2TP-клиент         --role client          (обфусци-     --role server      (xl2tpd)
 роутера)                                    рованный
                                             UDP)
```

Инструмент не разбирает PPP и L2TP — это просто UDP-труба, которая
преобразует всё, что получила с одного плеча, и отдаёт на другое.
Настоящим `pppd`/`xl2tpd` менять ничего не нужно, кроме адреса, по
которому клиент теперь подключается.

К каждому пакету добавляется собственный восьмибайтовый заголовок:
одноразовое значение и идентификатор сессии. Оба выводятся из ключа и
меняются от пакета к пакету, так что постоянных полей на проводе нет.
Накладные расходы — 8 байт на пакет поверх обычных UDP/IP, это же и
вся разница по MTU.

Идентификатор сессии нужен серверу, чтобы узнавать клиента по содержимому
пакета, а не по паре (IP, порт) внешнего UDP. Из-за этого смена порта на
NAT или возврат трафика после простоя не рвут туннель: сервер просто
переставляет адрес у существующей сессии. Подробнее — в описании
[`--session-id`](#справочник-флагов).

## Какой режим и роль выбрать

| Ситуация | Режим и роль |
|---|---|
| На машине уже есть настроенный `xl2tpd` (обычно VPS) | `--mode relay --role server` |
| На машине уже есть настроенный L2TP-клиент (обычно роутер) | `--mode relay --role client` |
| То же, но роутер Keenetic и настройка идёт через веб-интерфейс | `--mode relay --role keenetic` |
| Отдельная машина без готового PPP-стека, нужно поднять туннель «с нуля» | `--mode ppp` |

`relay` — основной и рекомендуемый режим: настоящий PPP остаётся видимым
и управляемым штатными средствами системы. `ppp` нужен там, где готового
PPP-стека нет и настраивать его отдельно неудобно.

## Настройка: режим `relay`

### relay — role=server

Запускается там же, где настоящий сервер, и слушает публичный порт.
`--target` указывает, куда отдавать расшифрованный трафик.

```sh
./hecate-eye --mode relay --role server \
  --listen 0.0.0.0:41850 \
  --target 127.0.0.1:1701 \
  --key '<общий секрет>' \
  --max-clients 8 \
  --idle-timeout 300
```

```ini
# server.conf
[main]
mode = relay
role = server
listen = 0.0.0.0:41850
target = 127.0.0.1:1701
key = <общий секрет>
max-clients = 8
idle-timeout = 300
verbose = info
```

### relay — role=client

Запускается там, где находится настоящий клиент. `--local` — адрес, на
котором `hecate-eye` ждёт этого клиента (именно его нужно прописать
клиенту как адрес сервера). `--peer` — адрес удалённого `role=server`.

```sh
./hecate-eye --mode relay --role client \
  --local 127.0.0.1:1701 \
  --peer 203.0.113.10:41850 \
  --key '<общий секрет>' \
  --session-id office-router
```

```ini
# client.conf
[main]
mode = relay
role = client
local = 127.0.0.1:1701
peer = 203.0.113.10:41850
key = <общий секрет>
session-id = office-router
verbose = info
```

Если настоящий клиент уже занял порт `1701` на всех адресах, выберите для
`--local` другой порт (например `127.0.0.1:9701`) и укажите клиенту
именно его.

### relay — role=keenetic

Частный случай `role=client` для роутеров Keenetic. Веб-форма настройки
L2TP-клиента отклоняет loopback как адрес сервера, а обычный адрес роутера
уже занят другими службами. `role=keenetic` решает это: поднимает себе
отдельный адрес в локальной сети роутера через пару veth-интерфейсов,
подключённую к указанному мосту, — и его уже можно вписать в веб-форму.

```sh
./hecate-eye --mode relay --role keenetic \
  --local 192.168.1.55:1701 \
  --peer 203.0.113.10:41850 \
  --lan-bridge br0 \
  --key '<общий секрет>' \
  --session-id keenetic-router
```

```ini
# keenetic-client.conf
[main]
mode = relay
role = keenetic
local = 192.168.1.55:1701
peer = 203.0.113.10:41850
lan-bridge = br0
key = <общий секрет>
session-id = keenetic-router
verbose = info
```

Имя моста (`--lan-bridge`) — это имя устройства в системе, а не в
интерфейсе Keenetic: смотрите `ip link show type bridge`, обычно `br0`.
В веб-интерфейсе роутера адресом L2TP-сервера указывается IP из
`--local` (в примере `192.168.1.55`).

## Настройка: режим `ppp`

Инструмент сам запускает и держит `pppd` через псевдотерминал. Всё, что
нужно передать `pppd` — аутентификацию, маршруты, MTU — задаётся
повторяемым флагом `--pppd-arg`.

### ppp — role=server

```sh
./hecate-eye --mode ppp --role server \
  --listen 0.0.0.0:41701 \
  --key '<общий секрет>' \
  --pppd /usr/sbin/pppd \
  --pppd-arg auth \
  --pppd-arg require-mschap-v2 \
  --pppd-arg nomppe \
  --pppd-arg noccp \
  --pppd-arg file --pppd-arg /etc/ppp/options.ppp-obf
```

```ini
# ppp-server.conf
[main]
mode = ppp
role = server
listen = 0.0.0.0:41701
key = <общий секрет>
pppd = /usr/sbin/pppd
pppd-arg = auth
pppd-arg = require-mschap-v2
pppd-arg = nomppe
pppd-arg = noccp
pppd-arg = file
pppd-arg = /etc/ppp/options.ppp-obf
max-clients = 8
idle-timeout = 300
```

### ppp — role=client

```sh
./hecate-eye --mode ppp --role client \
  --peer 203.0.113.10:41701 \
  --key '<общий секрет>' \
  --pppd /usr/sbin/pppd \
  --pppd-arg noauth \
  --pppd-arg name --pppd-arg myuser \
  --pppd-arg nomppe \
  --pppd-arg noccp \
  --pppd-arg file --pppd-arg /etc/ppp/options.ppp-obf.client
```

```ini
# ppp-client.conf
[main]
mode = ppp
role = client
peer = 203.0.113.10:41701
key = <общий секрет>
session-id = office-host
pppd = /usr/sbin/pppd
pppd-arg = noauth
pppd-arg = name
pppd-arg = myuser
pppd-arg = nomppe
pppd-arg = noccp
pppd-arg = file
pppd-arg = /etc/ppp/options.ppp-obf.client
```

> **`nomppe` и `noccp` обязательны на обеих сторонах.** Без них оба `pppd`
> пытаются согласовать дополнительное шифрование (MPPE/CCP) и не сходятся:
> соединение уходит в бесконечные повторы согласования. На передачу данных
> это не влияет, но лог засоряется полностью.

## Конфигурационный файл

Любой набор флагов выносится в текстовый файл:

```sh
./hecate-eye --config /etc/hecate-eye/client.conf
```

Правила формата:

- Каждая настройка — `имя = значение`, где `имя` совпадает с длинным
  флагом без ведущих `--`: `key`, `listen`, `lan-bridge`.
- Заголовок секции `[имя]` необязателен и игнорируется.
- `#` начинает комментарий — как в отдельной строке, так и в конце строки.
- Повторяющийся `pppd-arg` задаётся по одной строке на каждый аргумент, в
  нужном порядке.

Файл и флаги комбинируются в одном запуске — удобно, чтобы разово
переопределить параметр поверх файла:

```sh
./hecate-eye --config client.conf --verbose debug
```

## Справочник флагов

| Флаг | Где нужен | Описание |
|---|---|---|
| `--mode ppp\|relay` | всегда | Режим работы. |
| `--role client\|server\|keenetic` | всегда | Роль. `keenetic` — только с `mode=relay`. |
| `--key <строка>` | всегда | Общий секрет обфускации. Должен совпадать на обеих сторонах. |
| `--config <файл>` | опционально | Читать настройки из файла. |
| `--listen host:port` | `role=server` | Адрес, на котором слушает эта сторона. |
| `--peer host:port` | `role=client`, `role=keenetic` | Адрес удалённой стороны. |
| `--local host:port` | `mode=relay`, `role=client\|keenetic` | Адрес, на котором ждём настоящего локального клиента. |
| `--target host:port` | `mode=relay role=server` | Адрес настоящего сервера, куда отдавать расшифрованный трафик. |
| `--lan-bridge <имя>` | `role=keenetic` | Имя сетевого моста для собственного адреса. |
| `--lan-prefix N` | `role=keenetic` | Длина префикса подсети для `--local` (по умолчанию `24`). |
| `--pppd <путь>` | `mode=ppp` | Путь к исполняемому файлу `pppd`. |
| `--pppd-arg <значение>` | `mode=ppp` | Один аргумент для `pppd`; флаг повторяемый. |
| `--session-id <строка>` | `role=client`, `role=keenetic` | Постоянное имя этого клиента (см. ниже). Без него берётся случайное при каждом запуске. |
| `--max-clients N` | `role=server` | Максимум одновременных клиентов (по умолчанию `8`). |
| `--idle-timeout S` | `role=server` | Через сколько секунд **без трафика от клиента** освобождать его слот (по умолчанию `300`). |
| `--obfuscate-bytes N` | опционально | Маскировать только первые `N` байт полезной нагрузки (см. ниже). `0` — всю нагрузку, по умолчанию. |
| `--verbose <уровень>` | опционально | Уровень логирования (по умолчанию `info`). |
| `--help` | — | Краткая справка. |

**`--key`** — это секрет только для обфускации, не сертификат и не пароль
учётной записи. Он нужен, чтобы обе стороны одинаково преобразовывали
трафик, и не заменяет собой шифрование.

**`--session-id`** — сервер узнаёт клиента по идентификатору внутри каждого
пакета, а не по паре (IP, порт) внешнего UDP. Поэтому смена порта на NAT
или возврат трафика после простоя не выглядят для сервера новым пиром: он
переставляет адрес существующего слота и пишет в лог `session … moved
from … to …`. Идентификатор выводится из `--key` и этой строки, на проводе
он в каждом пакете выглядит по-разному, так что постоянного поля, за
которое мог бы зацепиться DPI, не появляется.

Задавайте `--session-id`, если хотите, чтобы клиент занимал один и тот же
слот и после собственного перезапуска. Без него берётся случайный
идентификатор: смену порта на NAT это по-прежнему переживает, а перезапуск
агента — уже нет, старый слот останется висеть до `--idle-timeout`. Разным
клиентам одного сервера нужны разные значения.

Слот на сервере освобождается по `--idle-timeout`, считая **только трафик
от клиента**: пакеты, которые сервер получает со стороны `--target`
(например, keepalive от `xl2tpd`), жизнь слота не продлевают — иначе слот
отключившегося клиента жил бы вечно.

**`--obfuscate-bytes`** — сигнатуру протокола распознаётся по началу
пакета, поэтому маскировать нагрузку целиком необязательно. Значение
вроде `32` ломает сигнатуру и при этом почти обнуляет стоимость
обфускации. Ограничение касается только полезной нагрузки: собственный
восьмибайтовый заголовок закрывается всегда и целиком, иначе
идентификатор сессии оказался бы на проводе открытым. Значение обязано
совпадать на обеих сторонах, иначе пакеты не расшифруются.

Все адресные параметры принимают форму `host:port`, где `host` — IPv4.

## Логирование

Уровень задаётся флагом `--verbose` или строкой `verbose = ...` в файле —
именем или числом. Каждый уровень включает всё, что показывают предыдущие.

| Уровень | Число | Что добавляет |
|---|---|---|
| `error` | 0 | Только ошибки. |
| `warn` | 1 | Предупреждения и сводку отбракованных пакетов (`drops:`). |
| `info` | 2 | Старт/остановку, подключение и отключение клиентов, смену их адреса, освобождение слотов. **По умолчанию.** |
| `debug` | 3 | Детали служебных операций и профиль конвейера (`ioprof`). |
| `trace` | 4 | Каждый пакет в обе стороны. Только для разбора проблем — очень многословно. |

Сообщения идут в stderr в формате `[роль][буква-уровня] сообщение`.

## Диагностика

### Счётчики отбраковки

В режиме `relay` раз в 5 секунд печатается строка `drops:` — но только
если за это окно что-то действительно было отброшено. **Молчание означает,
что конвейер не потерял ни одного пакета.**

| Счётчик | Что означает |
|---|---|
| `rx_overflow` | Ядро отбросило пакеты, не дойдя до агента: приёмная очередь сокета переполнилась. Признак нехватки процессорного времени — в том числе когда его отбирает гипервизор у виртуальной машины. |
| `runt` | Датаграмма короче обязательного заголовка (8 байт). Обычно посторонний трафик на порту. |
| `oversize` | Датаграмма не поместилась в приёмный буфер (2048 байт). Признак завышенного MTU на пути к локальному клиенту. |
| `undecodable` | Пакет не принадлежит известной сессии: не совпал ключ, данные повреждены в пути, либо на порт пришёл чужой трафик. |
| `replayed` | Пакет пришёл с чужого адреса и не продвинул счётчик сессии — повтор записанного ранее пакета. Сервер отбросил его, не переставляя адрес слота. |
| `tx_partial` | Ядро приняло не весь пакетный `sendmmsg` — переполнен буфер отправки. |
| `tx_error` | `sendmmsg` не принял ничего: порт недоступен, нет маршрута, переполнен буфер. |

Как читать: `undecodable` растёт при **повреждении** данных,
`rx_overflow` и `tx_*` — при **потере**. Причём `rx_overflow` указывает на
нехватку CPU, а `tx_*` — на переполнение буфера отправки.

### Предупреждения при старте

**`SO_RCVBUF clamped to ...`** — ядро урезало запрошенный буфер сокета, и
агент будет терять пакеты на всплесках трафика. Поднимите
`net.core.rmem_max`. Агент сначала пробует обойти лимит через
`SO_RCVBUFFORCE`, но это работает только под root.

**`net.ipv4.tcp_wmem max is ...`** — мал системный буфер TCP. Важно
**только если этот хост сам терминирует TCP через туннель** (его
собственные `curl`, `opkg`, `iperf3`); для транзитного трафика клиентов
локальной сети значения не имеет.

Причина: ppp-интерфейсы не поддерживают segmentation offload, поэтому
каждый TCP-сегмент занимает отдельный `skb`, а буфер расходуется по
`skb->truesize` — примерно в 1.7 раза быстрее, чем по объёму полезных
данных. На канале с большой задержкой этого достаточно, чтобы срезать
скорость вдвое при полностью свободных CPU и канале.

```sh
sysctl -w net.ipv4.tcp_wmem="4096 16384 16777216"
sysctl -w net.ipv4.tcp_rmem="4096 87380 16777216"
```

Чтобы пережило перезагрузку — в `/etc/sysctl.conf` или в
`/opt/etc/init.d/` на Entware.

### Профиль конвейера

На уровне `debug` раз в 2 секунды печатается строка `ioprof` по каждому
направлению: сколько пакетов и партий обработано и как распределилось
время.

> Все три времени — `recv_wall`, `work_wall`, `other_wall` — это
> **wall-clock фазы, а не процессорное время**. Поток, уснувший внутри
> системного вызова, даёт большой `work_wall` при почти нулевой загрузке
> CPU. Реальное потребление процессора смотрите в
> `/proc/<pid>/task/*/stat`.

Полезнее всего показатель `pkt/batch`: если он упирается в потолок партии,
направление не успевает разбирать очередь.

## Если что-то не работает

| Симптом | Вероятная причина | Что делать |
|---|---|---|
| Туннель не поднимается, в логе тишина | Не совпадает ключ или `--obfuscate-bytes` | Сверьте оба значения на обеих сторонах |
| Растёт `undecodable` при верном ключе | Данные повреждаются в пути | Проверьте, что обе стороны одной версии — формат провода менялся |
| `bind: Address already in use` | Порт `--local` уже занят настоящим клиентом | Выберите для `--local` другой порт и укажите его клиенту |
| Скорость низкая, CPU и канал свободны | Мал буфер TCP на конечной точке | См. [предупреждения при старте](#предупреждения-при-старте) |
| Растёт `rx_overflow` | Агенту не хватает процессорного времени | Проверьте `steal` на виртуальной машине; поднимите `net.core.rmem_max` |
| Растёт `oversize` | MTU на пути к локальному клиенту завышен | Уменьшите MTU туннельного интерфейса |
| `role=keenetic` не стартует | Нет `veth` или неверно указан мост | `ip link show type bridge`; на OpenWrt нужны пакеты `ip-full` и `kmod-veth` |
| После перезапуска агента туннель молчит, на сервере копятся `new session` | У клиентов нет `--session-id` или он одинаковый на нескольких | Задайте каждому клиенту своё постоянное значение |

Замеряя скорость, помните о двух ловушках, которые дают заниженный
результат: тест короче ~40 секунд на канале с большой задержкой меряет
разгон TCP, а не установившуюся скорость; а замер, где конечной точкой
выступает сам роутер, упирается в его собственные буферы и отсутствие
offload, а не в туннель.
